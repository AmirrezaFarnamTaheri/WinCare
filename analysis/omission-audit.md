## Omission-audit ladder

### 1. Files and links

All archive members were listed before extraction. Absolute paths, traversal, duplicate members, case collisions, links, device nodes, excessive expansion, and unsafe compression ratios were checked. No unsafe archive was admitted. Extracted donor file hashes are retained in the surface matrix.

### 2. Roots and packages

Repository roots, manifests, lockfiles, installers, build systems, release definitions, browser extensions, native binaries, screenshots/media, localization, docs, tests, fixtures, and administrative files were classified. Generated and vendored surfaces remain visible rather than being silently discarded.

### 3. Public/runtime surfaces

Entrypoints, download engines, stores, schedulers, launchers, plug-in/provider registries, monitor collectors, Steam parsers, window managers, offline servicing scripts, browser extensions, IPC/RPC surfaces, and bundled binaries were inspected and assigned dispositions.

### 4. Independent semantic contracts

Umbrella repository records were split into queue lifecycle, mirror/priority, scheduler, hash utility, browser-link admission, monitor counters, traffic history, fuzzy ranking, exact launcher identity, window zones, Steam manifest/conflict/VDF behavior, offline AppX/feature/component cleanup, and defensive game-integrity units.

### 5. State machines and recovery

Audited lifecycles include download queued/scheduled/transferring/suspended/completed/failed/cancelled/reconciled states; telemetry capture/history; launcher discovery/execution; Steam snapshot/backup/restore/rollback; mounted-image servicing; and layout create/update/apply/restore. Partial-failure windows and stale-preview races were mapped to internal rollback, compare-and-swap, or explicit irreversibility.

### 6. Negative paths and trust boundaries

Explicitly covered:

- HTTP downgrade and sensitive download headers;
- unbounded bytes, jobs, retries, mirrors, history, processes, files, and layout rules;
- destination replacement failure and partial finalization;
- corrupt/extra/traversing Steam ZIP entries;
- live Steam restore conflict;
- stale mounted-image/package/feature state;
- catastrophic regex behavior;
- stale HWND, process, monitor, or work-area identity;
- arbitrary launcher targets, shell command evaluation, remote providers, and clipboard monitoring;
- cheat execution, memory writing, DLL injection, anti-cheat bypass, and bundled-binary trust.

### 7. Operator surfaces

Each implemented plane is exposed through provider functions, TUI screens, command palette routing, headless JSON commands, reports, settings/policy where applicable, module exports, and focused test paths. Modifying headless commands require preview/apply and are excluded from the read-only broker.

### 8. Scripts, CI, packaging, and deployment

The release builder, source validator, evidence validator, adversarial archive tests, Windows validation orchestrator, CI, installer/uninstaller, internal manifest, SBOM, receipts, checksum, and provenance are included in the freeze gates. Donor installers/updaters do not become WinCare release authority.

### 9. Deep leaves

Deep test fixtures, localization, icon/media files, extension manifests, RPC definitions, packaging scripts, native headers, generated outputs, and example programs are present in surface accountability. They may be reference-only but are not omitted.

### 10. Historical and cross-wave claims

D01-D52 evidence is retained from the independently verified 4.2 bundle. D53-D86 is appended without rewriting prior source hashes or decision IDs. Cumulative counts are recomputed from the merged graph.

## Contradiction audit

- Downloader concurrency and retry semantics conflicted; WinCare uses the stricter configuration/policy intersection and bounded BITS jobs.
- Monitor projects mixed observation with “optimization”; WinCare separates read-only telemetry from mutation and rejects working-set folklore.
- Launchers mixed local exact targets with remote/network plug-ins; only deterministic local targets become executable.
- Zone tools depended on global hooks; WinCare uses explicit local invocation and exact recovery.
- Steam tools encouraged convenient synchronization; WinCare prioritizes local conflict evidence and closed-client restore.
- Image-reduction projects varied in serviceability; WinCare admits only exact supported identities and discloses irreversible operations.
- Cheat managers treated execution as product value; WinCare converts the same surfaces to defensive evidence and denied authority.
