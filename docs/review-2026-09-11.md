The application has confirmed release-blocking failures and significant gaps between its interface, diagnostic claims, and execution behavior. A visual refresh alone would leave the main problems intact.

Reviewed source: `b30516a`. Runtime evidence: the user's desktop `WinCare-v2.5.0-rc5-x64.exe`, supplied Home screenshots, local crash logs, and Windows Application Error events. The installed executable and current source are separate evidence sets; this review does not assume they are identical.

This is a broad evidence-backed review, not certification that every defect has been found. All 259 commands were not executed. Destructive operations, administrator changes, remote plugin installation, ARM64, upgrade behavior, screen readers, and every Windows configuration were not exercised. No application code was changed.

## Release blockers and misleading behavior

### 1. Checkup crashes the installed release [P1, runtime confirmed]

Two September 11 Application Error events identify rc5 and `Microsoft.UI.Xaml.dll`. Matching crash logs contain a `NullReferenceException` in `WinRT.TypeExtensions.GetAbiToProjectionVftblPtr`, while assigning `CheckupPage.ViewModel.CurrentRows` to `ItemsControl.ItemsSource`. The same stack also appears in a September 7 log.

Evidence: [latest crash log](C:/Users/ACER/AppData/Local/WinCare/Logs/crash-20260910-223002-667.log), [second crash log](C:/Users/ACER/AppData/Local/WinCare/Logs/crash-20260910-222912-130.log), [binding](D:/GitHub/WinCare/src/WinCare.App/Views/Pages/CheckupPage.xaml:122).

This is a UI/WinRT collection-marshalling failure, not evidence that the Windows command executor caused the crash. The portable profile enables trimming and suppresses trim warnings. That is an investigation lead, not a proven root cause. System Care, Security, Repair, and Activity share the same row-collection binding pattern and need artifact-level navigation tests. Do not suppress the fatal exception and continue in an unknown state.

### 2. The release gate does not exercise the failing page [P1, source confirmed]

[RunPortableSmokeTestAsync](D:/GitHub/WinCare/src/WinCare.App/App.xaml.cs:53) opens the shell, checks the native ABI, initializes plugins, runs a `system` preview, and exits. It does not navigate through Checkup or the other collection-backed pages. Unit tests link selected view-model files without loading the WinUI pages. A release can therefore pass these checks and still crash on its first meaningful navigation.

Required correction: test the final distributed artifact through every navigation route, typed input editor, theme, and principal read-only workflow. Retain trimming diagnostics until their consequences are understood.

### 3. The advertised preview-and-approval contract is not the actual policy [P1, source confirmed]

[Risk classification](D:/GitHub/WinCare/src/WinCare.CommandCatalog/Models/CommandDefinition.cs:117) makes moderate cleaner commands Safe based on their identifier prefix. [Dispatcher admission](D:/GitHub/WinCare/src/WinCare.Application/Commands/CommandDispatcher.cs:196) admits Safe mutations directly, and Moderate mutations require confirmation but not a previously issued review receipt unless one is supplied. [All Tools](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/ToolExecutionViewModel.cs:159) permits approval for Moderate tools before a successful preview and passes stored receipts only for Destructive tools.

Home, About, and README promise previews and explicit approval for all changes. These promises are false for the implemented policy. Align the policy, controls, tests, and copy; prefer a common review flow for mutations rather than command-name exceptions.

### 4. Quick Clean's normal launch experience conflicts with its promise [P1, source confirmed]

The Home and Checkup cleanup actions execute directly. The catalog requires administrator access, and the executor blocks unelevated execution with an instruction to restart elevated. There is no corresponding elevation handoff in these actions. Elevated execution can delete files immediately because of finding 3. Thus “SAFE · 1-CLICK” conceals both a prerequisite and the missing review step.

Sources: [Home action](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/HomePageViewModel.cs:131), [Checkup action](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/CheckupPageViewModel.cs:447), [elevation rejection](D:/GitHub/WinCare/src/WinCare.Infrastructure/Commands/WindowsCommandExecutor.cs:96).

### 5. Cleanup preview and execution describe different target roots [P1, source confirmed]

[Preview metadata](D:/GitHub/WinCare/src/WinCare.Infrastructure/Commands/WindowsCommandExecutor.cs:696) names `%TEMP%` and `%WINDIR%\Temp`. [Execution](D:/GitHub/WinCare/src/WinCare.Infrastructure/Commands/WindowsCommandExecutor.Experience.cs:303) uses the current temporary directory and LocalApplicationData/Temp. An approval view must be derived from the same resolved target set as execution.

### 6. Doctor fabricates a measured network observation [P1, source confirmed]

The [network evidence branch](D:/GitHub/WinCare/src/WinCare.Application/Diagnostics/DiagnosticEvidenceCollector.cs:32) creates a fixed DNS/socket message with `HasMeasuredEvidence: true`; it makes no network query. The default intent translator uses this collector. Remove the fabricated observation and represent unmeasured state explicitly.

### 7. All Tools can show values different from the values it will submit [P1, source confirmed]

Switching back from advanced JSON imports values into the field view models, but [generated controls](D:/GitHub/WinCare/src/WinCare.App/Views/Pages/AllToolsPage.xaml.cs:251) copy initial values and only wire control-to-model events. They do not subscribe to subsequent field changes, and switching modes does not rebuild them. This creates stale visible inputs. Use real two-way bindings or rebuild/resynchronize the editors after import.

The [import method](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/ToolExecutionViewModel.cs:425) also silently catches invalid JSON while the mode switch proceeds. The user can return to old structured values without an import error. Make conversion failure explicit and keep the editor in its current mode.

## Navigation and task completion

### 8. Five built-in category shortcuts produce no results [P1, verified against catalog]

`ToolCatalogService.Matches` treats the entire query as one substring. The embedded catalog returns zero matches for `storage cleanup`, `network update`, `defender firewall`, `export backup`, and `recovery reset`. These are the actual queries supplied by category pages. `startup applications` returns one match.

Sources: [search](D:/GitHub/WinCare/src/WinCare.Application/Tools/ToolCatalogService.cs), [System Care](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/SystemCarePageViewModel.cs), [Security](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/SecurityPageViewModel.cs), [Repair](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/RepairRecoveryPageViewModel.cs).

Use explicit category filters or command IDs for navigation, not informal search strings.

### 9. Category pages are static directories presented as workspaces [P2, source confirmed]

System Care, Security, and Repair construct fixed PageRows. Their status text does not come from completed checkups or command results; the page action generally forwards to All Tools. Security can continue saying “Not checked” after a check succeeds elsewhere. Undo and Routines contain empty static sections. These pages need live task state and direct task actions, or clear labeling as a directory.

### 10. Global search promises unsupported scopes [P2, source confirmed]

[The title bar](D:/GitHub/WinCare/src/WinCare.App/MainWindow.xaml:39) promises tasks, tools, settings, and activity. [Shell search](D:/GitHub/WinCare/src/WinCare.App/Views/ShellPage.xaml.cs:21) only opens the tool catalog. Settings and journal entries are not searched.

### 11. Empty global searches cannot clear an existing tool query [P2, source confirmed]

The shell forwards an empty string, but [All Tools navigation](D:/GitHub/WinCare/src/WinCare.App/Views/Pages/AllToolsPage.xaml.cs:36) applies only nonempty strings. A cached page retains its previous search rather than returning to all tools.

### 12. Home actions discard useful diagnostic results [P2, source confirmed]

Startup only displays the executor's entry-count message; it does not render the returned startup entries or measured startup impact. Network similarly discards the adapter data and labels any successful query “Connected,” even if the returned interfaces do not establish connectivity. “Startup Boost” and “Network Refresh” also suggest effects those read-only actions do not perform.

Source: [Home actions](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/HomePageViewModel.cs:162). Render useful findings and label actions by their actual effects.

### 13. Checkup permits overlapping update searches and offers no cancellation [P2, source confirmed]

The [update task](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/CheckupPageViewModel.cs:146) runs in the background with a 25-second deadline. `IsRunning` becomes false after the fast probes, enabling another check while the update task remains active. The version guard suppresses obsolete UI updates but does not stop the work. CancellationToken.None is used throughout this workflow. Keep explicit run state until every probe terminates, cancel superseded work, and expose cancellation.

### 14. Diagnostic summaries and result rows diverge [P2, source confirmed]

Checkup creates Results rows before evaluating disk and security findings. Evaluation updates the Quick check rows but not those copied Results rows. A problem can appear in the summary while Results only says “Collected.” Use one shared result model.

### 15. Cleanup success can conceal partial work [P2, source confirmed]

The cleaner catches inaccessible-file errors, counts skips, caps each enumeration at 200,000 files, and still returns success. Home reduces that to “Clean Complete” and hides the structured skipped count. Distinguish completed, partially completed, and bounded/truncated cleanup, and expose reclaimed bytes and omissions.

## Evidence quality and persistence

### 16. Doctor memory evidence is not a fresh system measurement [P2, source confirmed]

[ProbeMemoryUsage](D:/GitHub/WinCare/src/WinCare.Application/Diagnostics/DiagnosticEvidenceCollector.cs:122) uses GC memory information and treats missing/zero load as measured, healthy system memory. This data can reflect the last GC rather than current machine state. Use a fresh Windows probe and availability/timestamp metadata. The Doctor also counts every evidence record as a live probe, including records whose `HasMeasuredEvidence` is false.

### 17. CPU telemetry reports unavailable samples as real zeroes [P2, source confirmed]

[Native sampling](D:/GitHub/WinCare/native/wincare-core/src/telemetry.rs:106) returns zero for the first baseline and for GetSystemTimes failure, while overall snapshot success remains zero/status OK. [Home](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/HomePageViewModel.cs:244) marks CPU available whenever the aggregate call succeeds. Add per-metric validity and sample timestamps.

### 18. Disk telemetry is hard-coded to C: [P2, source confirmed]

The same native snapshot probes C: regardless of the Windows volume or cleanup target. The inspector presents that alongside generic cleanup target text. Report the actual volume identity and derive it from the relevant task.

### 19. Home combines arbitrarily old records into “current” evidence [P2, source confirmed]

[RefreshActivity](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/HomePageViewModel.cs:284) selects the newest record independently for each command without an age limit or check-run identity. Four results from unrelated dates can become 4/4, labeled using the newest timestamp. Display per-area freshness and preserve a coherent check session.

### 20. Health judgments use inconsistent and incomplete rules [P2, source confirmed]

Checkup classifies disk pressure with fixed 10/20 GB thresholds; Doctor uses 15 GB or 10%; the separate health handler uses 10%. They can disagree on the same drive. Checkup's final “Healthy” state does not incorporate every collected security field, including UAC, and equates stopped Defender with critical protection failure without assessing alternative protection. Centralize explicit findings and bound the language to what was actually checked.

Sources: [Checkup evaluation](D:/GitHub/WinCare/src/WinCare.App/ViewModels/Pages/CheckupPageViewModel.cs:303), [security probe](D:/GitHub/WinCare/src/WinCare.Infrastructure/Commands/WindowsCommandExecutor.System.cs:183), [Doctor storage probe](D:/GitHub/WinCare/src/WinCare.Application/Diagnostics/DiagnosticEvidenceCollector.cs:73).

### 21. Blocked attempts disappear from Activity [P2, source confirmed]

Dispatcher admission failures return before `_journal.Begin`. A rejected button action can therefore leave Home saying no activity has occurred. Record a distinct rejected outcome without falsely recording a mutation.

### 22. Normal shutdown does not flush the activity journal [P2, source confirmed]

[Window close](D:/GitHub/WinCare/src/WinCare.App/MainWindow.xaml.cs:66) flushes preferences but not the journal. Journal writes are queued asynchronously; late outcomes can be lost on exit. Add a bounded shutdown flush for all durable state.

### 23. Activity reports have an undisclosed short retention window [P2, source confirmed]

[The journal](D:/GitHub/WinCare/src/WinCare.Application/Activity/ActivityJournalService.cs:14) retains only 200 records, while Reports presents daily aggregates without explaining that older operations may have been evicted. Distinguish a recent-operation feed from a durable audit/report history.

## Visual design and accessibility

### 24. Home prioritizes decoration and secondary actions over starting a check [P2, screenshot and source confirmed]

The first-screen hero is informational; the “Run Checkup” button is below the action cards and additional panels. The supplied full-height screenshot does not reach it. Large empty card regions, thick double borders, repetitive status labels, and uniformly prominent teal buttons weaken hierarchy. Put one clear check action in the hero, reduce card padding/empty space, and render concise findings after the check.

### 25. Card headers cannot reliably fit at intermediate widths [P2, source-layout finding]

Home keeps three columns until the page is below 920 DIP. At 920 DIP, its 80 DIP padding and 32 DIP column spacing leave roughly 269 DIP per card before card padding. Each action header places a title/icon group and a right-aligned badge in the same Grid cell without reserving separate space. Overlap is structurally possible. Reflow according to actual card minimum widths; test intermediate sizes and increased text size.

### 26. The supplied image shows inconsistent button text contrast [P2, screenshot confirmed; cause unconfirmed]

“Analyze Startup” appears black on teal while adjacent primary labels are white. Current source uses the same style for these controls, so a unique hard-coded black label is not established. Capture normal, pointer-over, pressed, disabled, keyboard-focus, and high-contrast states from the release artifact before selecting a fix.

### 27. User-facing terminology exposes internals and overstates precision [P2, screenshot and source confirmed]

Home shows `cleaner-disk-pressure`, “dispatcher-issued preview receipt,” “NATIVE KERNEL TELEMETRY PROBE,” and microsecond latency where the user needs a task, impact, and result. The four-probe score sits next to six area tiles, including duplicated performance evidence and Activity; the relationship is unexplained. The three inspector buttons open the same inspector and carry the same accessible name. Use task-specific labels and place technical details in an optional diagnostics view.

The first two screenshots are the same scrolled Home view; content above the viewport is not, by itself, evidence of a clipping bug.

## Feature completeness and resource use

### 28. “Cleaner schedule” stores data without a scheduler consumer [P2, source confirmed]

The command writes a record to `cleaner-schedules`. No reader/execution loop for that state key was found in src or native. Persisting a schedule is not executing it. Either implement the lifecycle and runtime status or label this as a saved configuration with no automatic execution.

### 29. Guard notification delivery is incomplete [P2, source confirmed; documented limitation]

[Guard](D:/GitHub/WinCare/native/wincare-guard/src/main.rs:50) writes alert XML files to LOCALAPPDATA. No app consumer or app-side GuardPipeClient use was found. The code comment promises queuing for the app, but end-to-end display is not wired. Documentation calls Guard experimental; it must not be represented as active protection.

### 30. Plugin Store is not an operational remote store [product limitation, confirmed]

The composition root does not configure an approved catalog signing key, so remote installation is deliberately unavailable. This is correctly fail-closed, but a prominent “Plugin store” destination expands the perceived product beyond what is usable. Present installed-plugin management clearly and distinguish unavailable remote distribution.

### 31. Startup does work before asynchronous execution can yield [P2, source-path finding; duration unmeasured]

The first AppRuntime access constructs the catalog, journal, native/executor services, plugin registry, remote catalog, and installer. Plugin discovery begins from the UI startup path; uncontended semaphore awaits do not move directory enumeration or synchronous loading to a worker thread. The portable executable also uses compressed self-extraction. These are profiling targets, not proof of the user's sustained-load report. `StartupTelemetry` starts its clock at first class use, so its timings exclude earlier extraction/runtime startup.

### 32. Feature breadth exceeds validated user journeys [architectural assessment]

The shared WindowsCommandExecutor spans maintenance, security, updates, downloads, notes, color palettes, media, workspace tools, remote-consent state, and numerous specialist capabilities. Most reach users through a generic catalog/editor. The problem is not proven by line count or binary size: the concrete consequence is that static category pages and generic status messages substitute for task-specific completion flows. Reduce the supported product surface to workflows with working inputs, truthful previews, visible results, cancellation, and artifact-level tests. Keep specialist utilities secondary until those flows exist.

## Repair order and acceptance criteria

1. Fix and verify the released Checkup collection-marshalling crash. Navigate every page in the actual portable/MSIX artifacts, not only a debug build.
2. Establish one mutation review contract, align cleanup targets and privilege handling, and eliminate stale displayed inputs.
3. Remove fabricated evidence and distinguish failed, unavailable, partial, stale, and completed results.
4. Repair category routes and implement a small set of complete Home → check → findings → preview → action → result journeys.
5. Rebuild the visual hierarchy around those journeys; verify keyboard operation, screen readers, contrast, text scaling, and window resizing.
6. Profile cold startup and idle/active CPU, memory, GPU, and disk use with recorded budgets. Make background tasks cancellable and give them bounded lifetimes.
7. Reintroduce secondary capabilities only with truthful availability and end-to-end coverage.

Remaining deep validation: handler-by-handler behavior on disposable Windows machines, native ABI fault handling, plugin lifecycle faults, persistence under forced termination, multi-instance behavior, localization, high DPI/multi-monitor restore, ARM64, and installation/upgrade/rollback. Findings above are sufficient to block promotion; they are not a claim that unlisted areas are healthy.
